# 05 · Security and Auth

## Authentication and authorization

**There is none, by design.** The project scope explicitly excludes accounts, login and favorites. The consequences:

| Concern | Status | Why it doesn't apply |
|---|---|---|
| Identity verification | None | Every visitor sees the same public data |
| Sessions / tokens (JWT, cookies) | None | No server to issue or verify them; the app sets no cookies |
| Authorization / permissions | None | Nothing is private and nothing can be written |
| Credential storage | None | No user credentials. The external APIs used are keyless. |
| Auth middleware / route guards | None | All routes are public |

**Architectural reasoning:** the cheapest secure system is one with no attack surface. With a static host and read-only data, there is no server code to exploit, no database to inject into, and no secrets to leak. A future feature such as favorites should first consider `localStorage` (still no auth) before adding a backend.

## Attack surface that does exist

### 1. Rendering third-party text (XSS)

Descriptions, names and aliases come from Wikipedia and Sketchfab, which are crowd-sourced. The risk is cross-site scripting (XSS): injecting HTML or script that runs in a visitor's browser.

**Safeguard:** React escapes all interpolated values by default. `{car.description}` is inserted as a text node, never parsed as HTML. The codebase never uses `dangerouslySetInnerHTML`, so there is no path for raw HTML into the DOM.

The pipeline also requests **plain-text** sources: the REST `summary.extract` field (not `extract_html`), and section headings with tags stripped (`s.line.replace(/<[^>]+>/g, '')`).

### 2. URLs from third parties

Values used as `href`/`src`:

| Field | Source | Construction |
|---|---|---|
| `wikipediaUrl` | Wikipedia `content_urls` | Taken as-is from the API |
| `thumbnail`, `image` | Wikimedia `imageinfo`/`thumbnail` | API URL with the width rewritten |
| `sketchfab.authorUrl` | Sketchfab `user.profileUrl` | Taken as-is |
| iframe `src` | Built locally: `https://sketchfab.com/models/${uid}/embed?...` | Only `uid` (a hex id) comes from the API |

A `javascript:` URL in an `href` would be an XSS vector. These values come from trusted, well-formed APIs and are regenerated by a reviewed pipeline. React (v19) also blocks `javascript:` URLs in `href`. A stricter hardening step would be to assert `^https://` on every URL in the pipeline before writing.

### 3. Third-party iframe (Sketchfab)

```tsx
<iframe src={embed(car.sketchfab.uid)} allow="autoplay; fullscreen; xr-spatial-tracking" allowFullScreen />
```

- The iframe is **cross-origin**, so the browser's same-origin policy prevents it from reading the page's DOM, storage or cookies.
- `allow` grants only the features the viewer needs (autoplay, fullscreen, XR). The camera, microphone and geolocation are not delegated.
- It loads only on car pages that have a model, which also limits third-party cookies (Lighthouse flags Sketchfab's cookies; that's a privacy and performance note, not a vulnerability in this app).

### 4. Query-string input

The only user input is the search box and filter controls, all stored in the URL. That input is:
- Only ever compared (`includes`, `===`, numeric `>=`). It is never evaluated, used as a regex, or sent to a server.
- Coerced safely: years go through `Number(...) || 0`, and the page number is clamped to `[1, pages]`.
- Echoed into the UI only through React text nodes (`No cars match “{q}”`), so it's escaped.

### 5. Build-time supply chain

| Risk | Mitigation |
|---|---|
| Malicious npm package | Three runtime dependencies and a handful of well-known dev tools; `package-lock.json` pins exact versions |
| Pipeline secrets | None exist: all data APIs are keyless. The pipeline's `User-Agent` contains a contact email by API etiquette (Wikimedia's policy asks for one); it's not a credential. |
| Poisoned upstream data | Output is committed to git, so every data change is reviewable as a diff before deploy |

## What is intentionally absent

| Mechanism | Why absent |
|---|---|
| CORS configuration | CORS governs cross-origin requests to *your* server. The app only fetches same-origin static files. The pipeline calls third-party APIs from Node, where CORS doesn't apply. |
| CSRF protection | No state-changing requests exist |
| Rate limiting | A static CDN serves the files. Abuse protection is the host's job. |
| Input validation library (zod, etc.) | No untrusted input crosses a trust boundary into privileged code. The JSON comes from the repository itself. |
| Content-Security-Policy | Not configured. GitHub Pages can't set custom response headers, so a policy would go in a `<meta http-equiv="Content-Security-Policy">` tag in `index.html`. It would restrict `script-src` to self, `img-src` to self plus `*.wikimedia.org`, `frame-src` to `sketchfab.com`, and `font-src`/`style-src` to Google Fonts. |
